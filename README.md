# Music Discovery Backend

A Java/Spring Boot REST API that serves as the backend foundation for a larger music discovery platform.

Version 1 implements the first complete vertical slice of the application around **Artists** and **Songs**, including relational persistence, business logic, REST endpoints, validation, centralized exception handling, and automated testing.

The current project is intentionally focused on backend software engineering fundamentals. Recommendation systems, machine learning, frontend development, and other future features are outside the scope of Version 1.

## Architecture

The application uses a layered backend architecture:

```text
HTTP Client
    ↓
Controller + DTO Layer
    ↓
Service Layer
    ↓
Repository Layer
    ↓
JPA / Hibernate
    ↓
PostgreSQL
```

### Presentation Layer

Responsible for the REST API boundary.

Includes:

- REST controllers
- request DTOs
- response DTOs
- request validation
- HTTP status codes
- centralized exception handling

### Service Layer

Responsible for application and business logic.

Examples include:

- preventing duplicate artists
- preventing duplicate songs for the same artist
- verifying referenced artists exist before creating or updating songs
- coordinating repository operations
- throwing meaningful exceptions when resources do not exist

### Repository Layer

Uses Spring Data JPA repositories to provide persistence operations for domain entities.

Spring Data supplies implementations for common operations such as:

- `save`
- `findById`
- `findAll`
- `delete`
- `deleteById`

Custom derived queries are also used for business rules such as duplicate detection.

### Database Layer

PostgreSQL stores persistent application data.

Flyway manages schema evolution so database structure is reproducible and version controlled.

## Version 1 Domain Model

Version 1 contains two primary entities:

### Artist

```text
Artist
- id
- name
```

### Song

```text
Song
- id
- title
- durationSeconds
- artist
```

Relationship:

```text
Artist 1 ─────────── * Song
```

One artist can have many songs, while each song belongs to one artist.

In PostgreSQL, this relationship is represented by the `artist_id` foreign key on the `songs` table.

In Java, JPA maps the relationship using `@ManyToOne` and `@JoinColumn`.

---

## Database Schema

The initial Flyway migration creates the `artists` and `songs` tables.

```sql
CREATE TABLE artists (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    artist_name VARCHAR(200) NOT NULL
);

CREATE TABLE songs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    duration_seconds INTEGER CHECK(duration_seconds > 0) NOT NULL,
    artist_id BIGINT NOT NULL,
    FOREIGN KEY (artist_id) REFERENCES artists(id)
);
```

The schema includes:

- generated primary keys
- foreign-key relationships
- `NOT NULL` constraints
- string-length constraints
- positive-duration validation
- referential integrity

## Database Migrations

Database schema changes are managed using Flyway.

Migration files are stored in:

```text
src/main/resources/db/migration
```

Version 1 begins with:

```text
V1__create_initial_schema.sql
```

Flyway automatically applies pending migrations when the Spring Boot application starts.

DataGrip is used to inspect, query, and debug PostgreSQL, while permanent schema changes are made through Flyway migrations.

## DTOs

The REST API does not expose JPA entities directly.

Request and response DTOs define the API contract independently from the persistence model.

Example request flow:

```text
Incoming JSON
    ↓
CreateSongRequest
    ↓
SongController
    ↓
SongService
    ↓
Song entity
```

Example response flow:

```text
Song entity
    ↓
SongResponse
    ↓
JSON response
```

This separation prevents clients from directly controlling persistence-specific fields and allows the API and database model to evolve independently.

---

## Validation

Validation occurs at multiple layers.

### API Validation

Request DTOs use Jakarta Bean Validation annotations to reject malformed input before it reaches business logic.

Examples include:

- non-blank names
- non-blank song titles
- positive song durations
- required artist IDs
- maximum string lengths

### Entity Validation

Entities protect their own valid state through constructors and setters.

Examples:

- Artist name cannot be null or blank
- Song title cannot be null or blank
- Song duration must be greater than zero
- Song must reference an Artist

### Database Validation

PostgreSQL provides the final integrity boundary through:

- primary keys
- foreign keys
- `NOT NULL`
- `CHECK`
- relational constraints

## Exception Handling

The application uses centralized REST exception handling.

A custom:

```text
ResourceNotFoundException
```

represents requests for resources that do not exist.

Current mappings include:

```text
ResourceNotFoundException
→ 404 Not Found

IllegalArgumentException
→ 400 Bad Request
```

Example response:

```json
{
  "error": "Artist not found with provided id: 100"
}
```

This keeps exception-to-HTTP translation separate from controller and service logic.

## Running the Project

### Requirements

- Java 21
- PostgreSQL
- Maven or the included Maven Wrapper

Create a PostgreSQL database named:

```text
music_discovery
```

Configure the application datasource for your local PostgreSQL environment.

Example JDBC URL:

```text
jdbc:postgresql://localhost:5432/music_discovery
```

Run the application using the Maven wrapper on Windows:

```bash
mvnw.cmd spring-boot:run
```

Or run:

```text
MusicDiscoveryBackendApplication
```

directly from IntelliJ IDEA.

Flyway automatically applies pending migrations during application startup.

The REST API runs by default at:

```text
http://localhost:8080
```
